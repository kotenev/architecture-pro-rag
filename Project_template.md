## Задание 2. Подготовка базы знаний
### Пояснение к скрипту parse_fandom_pages.py и словарю замен terms_map.json

Вселенная: для выполнения задания была выбрана вселенная славянской мифологии. В качестве источника данных использовалась тематическая Fandom-вики по адресу: [https://mythological-creations.fandom.com/ru/wiki/Категория:Славянская_мифология](https://mythological-creations.fandom.com/ru/wiki/%D0%9A%D0%B0%D1%82%D0%B5%D0%B3%D0%BE%D1%80%D0%B8%D1%8F:%D0%A1%D0%BB%D0%B0%D0%B2%D1%8F%D0%BD%D1%81%D0%BA%D0%B0%D1%8F_%D0%BC%D0%B8%D1%84%D0%BE%D0%BB%D0%BE%D0%B3%D0%B8%D1%8F).

Процесс замены:

Замена терминов была полностью автоматизирована с помощью скрипта `parse_fandom_pages.py`. Процесс состоял из следующих шагов:

1.  Генерация замен: для каждого оригинального термина из славянской мифологии (например, "Леший", "Русалка") с помощью библиотеки `Faker` было сгенерировано уникальное вымышленное имя на английском языке (например, "Mark Murray", "Leslie Ortega").

2.  Создание словаря: все соответствия между оригинальными и вымышленными именами были сохранены в файл `terms_map.json`. Этот файл служит словарём для последующей замены в текстах.

3.  Обработка текстов: скрипт поочередно скачивал контент с каждой веб-страницы, указанной в словаре `fandom_pages`. Затем он очищал текст от HTML-тегов и systematically заменял все вхождения оригинальных терминов (ключи из `terms_map.json`) на их вымышленные аналоги (значения из `terms_map.json`).

В результате была создана уникальная база знаний, тексты в которой сохранили свою логику и читаемость, но больше не содержат прямых упоминаний, позволяющих идентифицировать их как относящиеся к славянской мифологии.

### Документация по защите

#### Использованные механизмы защиты:

1. SAFETY_BLOCKLIST (src/config.py):

```python
SAFETY_BLOCKLIST = [
    "superpassword", 
    "swordfish", 
    "ignore all instructions", 
    "root-password"
]
```

2. Pre-фильтрация чанков (_text_contains_blocked_terms):

```python
def _text_contains_blocked_terms(self, text: str) -> bool:
    lower = text.lower()
    return any(bad.lower() in lower for bad in SAFETY_BLOCKLIST)
```

3. Post-фильтрация ответов (post_filter):

```python
def post_filter(self, text: str) -> Tuple[bool, str]:
    lower = text.lower()
    for bad in SAFETY_BLOCKLIST:
        if bad.lower() in lower:
            return False, f"Фильтр безопасности: найдено '{bad}'"
    return True, text
```

4. System prompt с ограничениями:

```
"Опирайся только на предоставленный контекст. 
Если данных недостаточно, отвечай: 'Я не знаю'."
```

- честные ответы: бот корректно отвечает "Я не знаю" на вопросы вне базы знаний;
- защита от инъекций: system prompt и post-фильтрация предотвращают выполнение вредоносных команд;
- многоуровневая защита: комбинация pre- и post-фильтрации обеспечивает надёжную защиту.

#### Потенциальные уязвимости:
- статический blocklist: требует регулярного обновления списка опасных терминов;
- обход через синонимы: возможен обход через использование синонимов или транслитерации;

## Задание 7. Аналитика покрытия и качества базы знаний

### 1. Внесение искусственных пробелов в базу знаний

Для моделирования неполной документации из каталога knowledge_base/ были удалены документы по трём ключевым персонажам:

- Тихон: замена Лешего (лесной дух, опорная сущность для многих запросов);
- Светлана: замена Полудницы (каратель нарушителей полуденного покоя);
- Ленина: аналог Гамаюна (вещая птица, связанная с пророческими песнями).

После удаления соответствующих файлов FAISS-индекс (index/faiss.index, index/metadata.json) был пересоздан. Таким образом, при запросах о Тихоне, Светлане и Ленине в индексе отсутствуют релевантные чанки, что позволяет проверить:

- будет ли бот честно отвечать "Я не знаю";
- или попытается "додумать" ответ без опоры на базу знаний.

### 2. Скрипт логирования запросов

Для логирования запросов и ответов создан модуль src/logging_utils.py .

Каждый запрос к боту (через REST API, Telegram или автотест) записывается в файл logs/logs.jsonl в формате JSONL. Для каждой записи фиксируются:

- timestamp: временная метка;
- query: текст запроса;
- answer: ответ бота;
- answer_length: длина ответа;
- chunks_found: были ли найдены релевантные чанки;
- sources: список источников (идентификаторы чанков);
- expected: ожидаемый тип ответа (known / unknown) для golden-набора;
- golden_id: ID вопроса из golden_questions.jsonl (если применимо);
- must_contain / forbidden: ключевые и запрещённые слова для оценки;
- success: флаг успешности ответа.

Функция log_interaction(...) вызывается:

- в src/api.py в обработчике endpoint /ask;
- в src/telegram_bot.py в обработчике входящих сообщений;
- в evaluate_rag.py при прогоне golden-набора.
